# 夜莺码表维护交接手册（换到 Mac 上用）

写于 2026-09-27，当前对外版本 2.5。在 Mac 上接手维护的人（或 AI）先读这一篇，再按需要翻 `码表概念与规则.md`（规则本身）和 `00_维护/README.md`（两步维护的最短说明）。

---

## 一、先说清最容易出事的一点：哪一份是原本

以前 Windows 上有两份：**E 盘的工作区**（真正干活的地方）和 **D 盘的仓库副本**（`D:/nightingale`，用 `116_仓库同步/sync.py` 从 E 盘单向镜像过去，再 git 提交）。Mac 只能从 git 拿数据，所以：

> **从现在起，git 仓库里的 `work/夜莺2.0/` 就是唯一原本。Mac 上直接在仓库里改。**

由此两条铁律：

1. Mac 上**不要再运行** `116_仓库同步/sync.py`。它是 `E:/夜莺2.0 → D:/nightingale` 的单向覆盖，在 Mac 上跑只会把东西写到不存在的盘，或者（如果有人把它改成新路径）用旧副本盖掉新改动。
2. 以后若再回 Windows 上干活，**先 `git pull`，并且从仓库里干活**，不要再在 E 盘那份上改。E 盘那份从 2026-09-27 起就是过期副本。

## 三、Mac 上第一次要做的事

1. **克隆仓库**：`git clone https://github.com/losWater/Nightingale.git`，下面用 `<仓库>` 指它的根目录。工作区在 `<仓库>/work/夜莺2.0`。
2. **装 Python 3**（3.10 以上都行）。日常维护只用标准库；`140`/`141` 审计脚本要 `pyyaml`，需要时 `pip install pyyaml`。
3. **改写死的路径**（只有这几处，见第七节表格）。最省事的做法：在 `00_维护/版本.py` 里加一行仓库根目录，让 `117`、`118`、`144` 都从那里取，而不是各自写死 `D:/`、`E:/`。
4. **验一下能不能读表**：`python 00_维护/apply_ledger.py`。台账里没有待处理行时，它只做体检并打印「没有待处理的行」，不写任何文件。这一步过了，说明表和脚本都正常。
5. **不要指望第一天就能完整发版**，缺三个大文件（第六节），补齐之后才能生成 Rime 全套。

## 四、日常维护：两步，永远只有两步

### 第一步 改主表（`00_维护/apply_ledger.py`）

1. 你的原始反馈用白话记在 `releases/v2.5/用户实战反馈.txt`（手写文件，脚本从不碰它）。
2. 把每条反馈翻译成台账 `00_维护/实战问题机器参数.tsv` 里的几行，状态写「待处理」。字段顺序固定：
   `问题ID 原文摘录 状态 目标码表 操作 原编码 原字词 新编码 新字词 目标候选位 备注 处理时间 处理结果 修改前SHA256 修改后SHA256`
   - 目标码表：`单字表` / `字词表` / `符号表`
   - 操作：`查询`、`新增`、`删除`、`改码`、`改词`、`调序`
   - 候选位 = 同一个码里的第几个（字词表里字和词一起数）
   - **单字的改动要在单字表、字词表各写一行**，两表必须一致，否则体检不过
3. `python 00_维护/apply_ledger.py` 先预演，逐行看结果；确认无误再 `python 00_维护/apply_ledger.py --apply`。落盘时自动备份到 `00_维护/备份/时间戳/`，并把时间、结果、前后 SHA256 回填进台账。没被点名的行一个字节都不会动。

### 第二步 生成各输入法格式（`00_维护/export.py`）

```
python 00_维护/export.py              # 只生成
python 00_维护/export.py --deploy     # 再更新本机输入法（Mac 上跑不了，见第六节）
python 00_维护/export.py --release    # 再组装发布目录和官网数据
```

它只读主表（跑完会校验主表 SHA256 没变），任何一步失败就停。里面依次做：主表结构体检 → 规则体检（78 的 14 项，**只报告不拦**，因为人工裁定可以高于规则）→ 拆分同步 → 106 全平台导出/引擎核验/打包 → 114/115 工具箱 → 123 虎娘 → 137 虎娘单字版 → 125 码圈 → 131 鲸凉鹤专属 → 127 Rime 主力版。每次运行往 `00_维护/导出记录.jsonl` 追一行。

### 只改拆分显示（编码不变）

`python 00_维护/改拆分.py 字=根＋根 --apply`。它只改啾啾工具箱那一份原本，`sync_chaifen.py` 再把其余八处副本对齐（export.py 里已经带这一步）。如果拆分改动让首根或末根变了，**编码也得改**，那就照第一步走台账。

## 五、发版顺序（顺序错了日志就是旧表的）

版本号只有一个出处：`00_维护/版本.py` 里的 `VER`。发新版只改这一行（`DATE` 自动取当天）。方案名 `yeying20`、包内「夜莺2.0」这些内部标识**故意不跟着改**，为的是老用户能直接覆盖安装。

1. `python 117_发布v2.0/build_release.py` —— 组装发布目录
2. `python 143_2.5更新日志/对比.py` 再 `python 143_2.5更新日志/写日志.py` —— 拿新发布目录和上一版综合表对比、写更新日志（md + txt）
3. **再跑一次** `build_release.py` —— 把刚写出来的日志收进发布目录
4. `python 117_发布v2.0/upload_release.py` —— 传 GitHub Release 附件（需要 `gh` 命令行并已登录）
5. `python 118_官网2.0/compute_performance.py`、`python 118_官网2.0/sync_to_repo.py` —— 官网数据
6. git 提交推送

git 有两条规矩：**绝不 `git add -A`**（仓库里散落着上 GB 的未跟踪大文件，曾经一次误加 1.2GB），也别 `git add -f` 发布大包。按路径 add，并且过滤掉 50MB 以上的文件。分支是 `main`。

## 六、Mac 上跑不了的、以及怎么办

| 跑不了的 | 为什么 | 怎么办 |
|---|---|---|
| `00_维护/deploy_local.py`（本机部署） | 里面调小狼毫 `WeaselServer.exe`/`WeaselDeployer.exe` 和虎娘 `Tigirl.Import.exe`，都是 Windows 程序 | Mac 上别加 `--deploy`。自己试打就手动把 `106_全平台导出/Rime_轻量版` 拷进鼠须管用户目录（`~/Library/Rime`）重新部署 |
| 引擎核验（`106/verify.py`、`127/verify.py`） | 用 `D:/nightingale/.tmp/rime_bench.exe` + 小狼毫运行库，Windows 专有 | 要么在 Mac 上用 librime 自己编一个同样接口的 bench，要么把 export.py 里这两步临时跳过——**跳过就等于没核验，只改表顺序时风险不大，改方案/lua 时别跳** |
| `106/build.py` 整体 | 它从 `releases/v1.0/.../发布包/Nightingale-Rime-1.0-{light,main}-f2-20260911.zip` 里取 1.0 的运行库，这两个 zip（398MB）不在 git 里 | 从 GitHub 上 v1.0 的 Release 下载这两个 zip，放回同一个相对路径 |
| 手机版（106 尾段） | 需要 `106_全平台导出/models/wanxiang-lts-zh-hans.gram`（约 420MB，来自 amzxyz/RIME-LMDG），不在 git 里 | 下载放回该路径 |
| Rime 主力版（127） | 需要 `127_魔虎基座试验/upstream/`（魔虎基座包 + `mohu-sentence-ngram-v5.bin` 模型，约 1GB），不在 git 里；而且魔虎 V5 引擎只有 Windows x64 原生库 | 要发主力版就下载魔虎的包（github.com/fcxxxz/rime-mohu）放回 `upstream/`。**主力版本身在 Mac 上没法实机验证** |
| `138_虎娘皮肤` | 直接改 Windows 版 Tigirl.dll 里的调色板 | 放弃，纯个人皮肤，不影响码表 |
| `144_晴跟打词提` 的复制目标 | 写死了 Windows 上晴跟打的目录 | 文件照样生成在 `144_晴跟打词提/` 下，把复制那一步的路径改成 Mac 上的位置或注释掉 |

**结论**：Mac 上表层的维护（改码、调序、改拆分、生成虎娘表/码圈/鲸凉鹤/词提/更新日志）完全没问题；**要完整发一次版，得先补齐上面三个大文件**（1.0 的两个 zip、万象 gram、魔虎 upstream）。

## 八、不能破的规矩

- **主表冻结**：只用台账改那三张表，改完用 export.py 导出。不许再从生成链重算。
- **字的简码从不让位**：让位规则只有《码表概念与规则》第五节那三条，且只管四码位。别自己发明让位规则。让位阈值是前 5000（2026-09-22 比过 6000，维持 5000）。
- **简码归属是人工裁定**：审计脚本只能列候选，不许机械批量改，那会毁掉人工定稿。
- **布局已冻结**：字根键位不再重跑退火（搬根收益上限 0.14%，不值当）。
- **夜莺是挂接方案，不是四码定长**：字词表里 223 条超过四码的词是正常数据（从鲸凉鹤继承），不要当错误删掉。个人想要四码顶屏，在输入法里把最大码长设成 4。
- **不符合原则的现象先查根因**，不要用特例去盖。
- **脚本不许删用户手写的文件**：只按自己的清单清理自己生成的东西（2026-09-16 曾经误删过手写反馈文件）。
- **每次改动，动的文件最少、步数最少**。不追求处处严丝合缝——已经进入长期维护，不会再重新生成什么。

## 十、出问题怎么退回去

- 改主表出错：`00_维护/备份/` 下按时间戳存着改动前的三张主表和台账，拷回去即可；台账里也记着每次的前后 SHA256。
- 导出产物出错：删掉产物重跑 export.py，它不改主表。
- 已经提交到 git：`git revert` 对应那次提交。已经传上 Release 的附件，重跑 `upload_release.py` 会 `--clobber` 覆盖。
