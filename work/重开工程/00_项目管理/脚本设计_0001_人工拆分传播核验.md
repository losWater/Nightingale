## 要解决的唯一问题

找出每条人工规范拆分的真实命中和传播范围，并检测应用人工规则却被绕过、零命中、或被其他规则覆盖的字。

## 权威输入

1. `01_根集/根集_待完整性复核.yaml`：候选根集。
2. `02_规范拆分/人工规范拆分_待验收.yaml`：只含结构层规则。
3. 8105 字字集：从 `02_规范拆分/最终规范拆分表_待核验.tsv` 的“汉字”列读取；仅用字集，不把其拆分结果当作期望答案。
4. 仓库中已固定版本的 hanzi-chai 字形数据和组装器；这是上游引擎，不属于夜莺历史脚本。
5. `04_Chai输入/结构分析基线_待审计.yaml`：只作为 Chai 字库、自定义字形、
   变换器、分类器、退化器与选择器的结构基线；核验脚本会重新生成根映射和
   `analysis.customize`，不得继承其中旧的根映射或人工拆分。

上述结构基线迁自 `work/seed.yaml`。迁移仅用于让当前 8105 表具备可复现的
同条件反事实环境；它仍标记为“待审计”，报告必须记录其 SHA-256，不得将其
静默视为已经验收的权威资产。

## 核心方法

对每条 `P → S`人工规则分别运行三个同根集反事实：

1. **AUTO**：不带任何人工拆分。
2. **ONLY-P**：只带当前 `P → S`。
3. **ALL**：带全部人工规范拆分。

判定：

- `ONLY-P != AUTO`：字进入该规则的真实命中集。
- `ONLY-P == AUTO`且部件本身结果不等于声明序列：零命中或规则无效。
- `ONLY-P` 下部件本身等于声明序列：规则直接生效。
- 命中字在 `ALL != ONLY-P`：可能被另一条规则覆盖或产生交互，单独列出。
- 部件被已成根的更大结构遮蔽时，不得误报为绕过；报告为“合法不适用”并给出遮蔽根。
- 人工拆分可以含非根的中间部件；不得仅因该名称未出现在最终根序列就判定规则失效。
- 必须将“结构规则已生效”与“经根集取根后的最终根序列正确”分成两项验收。
- 若 `canonical_root_overrides` 声明某字的正确最终根序列，ALL 结果必须与之精确相等。

## 预期输出

1. `02_规范拆分/人工拆分传播核验.md`：人工阅读总报告。

4. 每条规则必须报告：声明拆分、AUTO直接结果、ONLY-P直接结果、命中字、ALL交互字、零命中或不可解析错误。

## 不得修改

- 根集。
- 人工规范拆分输入。
- 8105 字待核验表。
- 任何历史资产。
- hanzi-chai 源码与字形数据。

## 必须通过的验收

1. 输入字集必须恰为 8105 个不重复字形。
2. 每条规则的左侧部件和右侧元素必须能被 hanzi-chai 唯一解析；右侧可为中间部件，不强制其本身是根。无法解析时失败，不得静默跳过。
3. AUTO、每个 ONLY-P 与 ALL 运行都必须完成8105字，不得沿用上次中间文件。
4. 每次运行保存输入 SHA-256、引擎 Git 提交及运行时间。
   若引擎工作区有本地修改，还必须保存 `git diff` 的 SHA-256、修改文件列表，
   并在报告中明确标记为 dirty，不得只记录提交号。
5. 人工拆分零命中、无法解析、部件自身不符声明、规范根序列覆写未落实或运行数量不完整时，脚本必须以非零状态退出。

6. TSV、Markdown与JSON的规则数、命中数和异常数必须一致。
